# Roadmap

Open work, sequenced for execution. Items get deleted as they ship. Architectural decisions live in `docs/decisions.md` (ADRs); user-facing usage in `docs/architecture.md`, `docs/chat-ux.md`, `docs/mobile-ux.md`, and `docs/mcp.md`. Schema reference: `packages/shared/src/db/schema.ts` (Drizzle).

## Cloud / SaaS (shape agreed, not yet sequenced)

Friday becomes a SaaS product: cloud-first, one **Deployment** (a container
stack plus Postgres) per customer **Organization**, several **User**s
collaborating through one shared Friday. Local install demotes to a dev
fallback. See `CONTEXT.md` (Deployment and identity, Transports) for the
vocabulary.

- **Control plane — a second application, not a Friday feature.** Instance-per-customer
  needs a separate multi-tenant app that owns everything a customer meets before
  they have a Deployment: public marketing, self-serve **registration**, billing,
  legal (terms/privacy/DPA), and support. It is also the thing that **initializes a
  new Deployment** on signup — create the database, provision the role and the
  `vector` extension, create `friday_pub`, allocate a replication slot, generate the
  per-Deployment secrets (`BETTER_AUTH_SECRET`, `ZERO_AUTH_SECRET`, daemon secret,
  age vault identity, VAPID keypair), allocate a hostname and certificate, then boot
  the stack. Today that work is `friday setup`, an interactive wizard. Nothing in
  this repo does any of it unattended.
- **A Deployment is one container; Postgres is external.** The supervisor runs as PID 1 managing daemon + zero-cache + dashboard, mirroring today's process model. Not split per-process, because **loopback is a load-bearing authorization boundary**: the daemon binds strictly to `127.0.0.1` and checks a localhost `Host` header, `/api/mutators` and `/api/internal/capture-keys` are exempted from the session gate by `isLoopbackOrigin()`, and `/api/mutators` — the endpoint every write goes through — has no session authorization at all beyond being loopback-only. Separate containers would mean replacing an origin check with real service-to-service auth on the most privileged endpoint in the system, bought for scaling benefits that are worthless at one customer per instance. Postgres stays external because `CREATE EXTENSION vector` needs SUPERUSER (ADR-044), `wal_level=logical` is a server-level setting, and it is the only canonical state — the Zero replica can be discarded and rebuilt, the database cannot. Persistence to plan for: `~/.claude/projects` needs a real volume (it is outside `FRIDAY_DATA_DIR` and holds SDK session transcripts — without them every **Conversation** silently starts fresh after a deploy), while `~/.friday/zero` can be ephemeral.
- **Departure and cancellation.** A **User** who leaves is **revoked, not erased**: sessions revoked (`revoke`/`revoke-all` exist), devices forgotten (`client_devices.revoked_at`), **Capture key**s revoked (the BetterAuth apiKey plugin has this built in), and all their data preserved — personal-**Scope** rows included. This keeps "Preserve over delete" intact and keeps the **Organization**'s record whole; the Organization is the data controller, so an individual's erasure request goes to their employer, not to us. **But the capability must still exist**: an admin needs an explicit per-User erasure action to honour a controller instruction when it comes, which is a second reason the acting-User stamp is a prerequisite rather than hygiene — `memory_entries.created_by` holds an _agent_ name, and you cannot delete what you cannot attribute.
  An **Organization** that cancels enters a **retention window** rather than immediate deletion — the Deployment is _suspended_, which is the same state the Control plane's kill switch already needs for non-payment and abuse. Three actions available in the window: **(1) restore the account** (unsuspend, nothing lost), **(2) export their data**, and **(3) delete immediately**, skipping the rest of the window. **2 then 3 is the expected path** — so export must be asynchronous (it can be large), and an immediate delete that follows an export has to wait for that export to complete and be confirmed retrieved, or the customer loses data they asked for. `friday backup --full` is a real head start, and notably already captures `~/.claude/projects` transcripts because without them restored sessions start fresh.
  Deletion must reach four things outside Postgres, or it deletes an index rather than the data: the **data-dir volume** (`memory/entries/*.md`, `uploads/`), the **SDK transcripts** at `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl` (one long-lived session per User-agent pair, holding the verbatim conversation), the **Zero replica and replication slot**, and the Deployment's **secret-manager entries**. Wrinkle: `attachments` is content-addressed by `sha256` with no owner column, so two Users uploading the same file share one row and one blob — per-User attachment deletion is ambiguous by construction and needs either an upload-attribution join table or an accepted rule that blobs are org-**Scope** and only the reference is personal.
- **Fleet upgrades are the accepted cost of instance-per-customer.** Each release is
  N independent boot-time migrations against N databases. The consequences are
  known and chosen: expand/contract migration discipline becomes mandatory (version
  skew is permanent — the fleet is never updated atomically), schema rollback does
  not exist (roll forward only), and the ADR-044 self-referential update gap means a
  fix to the rollout mechanism cannot apply to the rollout that delivers it. Needs
  canary cohorts, per-Deployment migration telemetry, and synthetic per-tenant health
  probes — process liveness is not enough, because the worst failure (Zero schema vs.
  `friday_pub`) leaves the page looking fine while live sync is dead.
- **Ingress: per-Deployment hostname for humans, one central shim for integrations.** Cloudflare Tunnel does not survive the move — it is installed via `cloudflared service install` into `~/Library/LaunchAgents` and driven by `launchctl`. Humans reach `<org>.friday.app` directly (wildcard TLS, routed by `Host`), because SSE and the Zero WebSocket are long-lived and because BetterAuth resolves `baseURL`/`trustedOrigins` from the public URL and **hard-exits with `process.exit(1)`** on a mismatch — so a hostname change is a restart-with-new-config, not a runtime setting. Webhooks cannot be per-Deployment: a distributed Slack app has exactly **one** Event Subscriptions URL for all installs (same for GitHub Apps and OAuth redirect URIs), so all integration traffic lands on one shared endpoint, is signature-verified once, and is routed by `(provider, external_workspace_id) → Deployment`. Build that shim as a **separate, minimal service** from the rest of the Control plane — stateless verify-and-route, no billing DB — because it is a _runtime_ dependency for every **Transport**, unlike login, which survives a Control-plane outage on existing sessions. Custom domains (`friday.acme.com`, per-customer ACME) are a later enterprise upgrade.
- **Per-Deployment Claude auth and spend has no implementation.** Agent auth today is
  the locally-logged-in `claude` CLI Pro/Max subscription (`doctor` hard-checks
  `which claude`; the SDK gets the host login shell's env), which cannot serve N
  customers.
  Decided: **Capacity source** is per-Deployment, either `friday` (our org keys, billed
  through the **Control plane**) or `byo` (the customer's own key in their vault — the
  `ANTHROPIC_API_KEY` vault plumbing partly exists), with a **Usage cap** enforced in
  **both** modes. Enforcement must sit in the **dispatch path**, not a reconciliation
  job: the scheduler fires on a 30s tick with nobody watching, `usage`/`usage_request`
  are written _after_ a turn, and the `worker.turn.stalled` watchdog detects liveness,
  not spend — so a looping agent can burn a month's budget in an hour unnoticed. The
  Control plane owns the ceiling and the kill switch (suspension for non-payment, abuse,
  or a blown budget). A free trial needs a token ceiling, not just an expiry date.
- **Per-User read/write enforcement has no implementation.** Every Zero-synced table is `{ row: { select: ANYONE_CAN } }` ("Friday is single-user... every authenticated client reads every row"), and the dashboard adds deliberately global queries in `#bindReadCursors`/`#bindClientDevices`. With per-**User** **Conversation**s that means one employee's client replicates another's private blocks. Needs: row predicates on the `personal`-**Scope** tables (the Zero JWT already carries `userId`, so the input exists), plus ownership checks in the mutators — Zero has no insert/update/delete row rules at all, so writes are authorized solely by mutator functions and none of them check ownership today.
- **Stamp the acting User now, filter later.** `memory_entries.created_by`, `ticket_comments.author`, and `mail` attribute to _agent_ names; `blocks.user_id` exists but is attribution-only. Authorship not captured cannot be backfilled, so record it on the org-**Scope** tables even while they stay org-visible.
- **Evolve narrows to what a Deployment can actually act on.** `evolve_proposals` carries five types — memory, docs, code, prompts, tooling — and four of them propose changes to _the product_, not the customer's data: code ships as an immutable image (patching it in place breaks the one-image invariant and every fleet update), `CONSTITUTION.md` and `agents/<type>.md` are code-owned and never copied into `~/.friday/`, and docs/tooling are the repo. Only **memory** is unambiguously the customer's own. Ship: memory hygiene, consolidation, the Dream Diary, and org-level prompt tuning through the admin-owned `SOUL.md`. Drop the code/docs/tooling paths from the product surface. Applying a proposal becomes **admin**-only per the **Role** split, and `evolve_critical`'s DND bypass needs rethinking — "Friday wants to change itself" is a reasonable 3am interrupt for a maintainer and an odd one for an employee.
- **Fleet learning is an important upgrade path (the deferred evolve option (c)).** A Deployment that notices friction reports it upward, so the fleet informs product development — and eventually so Friday's shipped behaviour improves from aggregate patterns. Two distinct goals worth not conflating: **federated analytics** (which frictions are common across Deployments, informing our roadmap — achievable, low risk) and **fleet-informed behaviour** (shipped prompts and heuristics improving from aggregates — closer to federated learning proper, needs far more care). The enabling design constraint, cheap now and expensive to retrofit: **a privacy-preserving channel needs a code-owned taxonomy, not free-text proposals.** Proposals today are prose derived from customer transcripts and can never be safely exported whatever is layered on top; a Deployment emitting a classification against a fixed vocabulary shipped in the image ("friction class N occurred k times") can be aggregated and noised. So scanners would classify against that vocabulary while the prose proposal stays local. Opt-in, with consent and a privacy-policy line, never inherited by leaving the pipeline switched on.
- **Audit needs the acting human, not just the acting agent.** `secrets_fetch_log` records `caller_name`/`caller_type` — i.e. "orchestrator fetched the Linear API key," with no record of which **User** asked. Same gap in `memory_entries.created_by` and `ticket_comments.author`, which hold agent names. A company cannot currently answer "who asked Friday for our credentials," which is a day-one audit question.
- **Postgres: shared cluster now, dedicated servers as an upgrade.** Start with one cluster hosting a database per **Deployment** (everyone treated as a trial), then add the shared→dedicated migration path incrementally — dump, restore, swap the connection string, re-COPY the Zero replica. Required up front, not deferrable: (1) `FRIDAY_DB` and the connection string become configuration — `postgresql://${process.env.USER ?? "postgres"}@localhost:5432/${FRIDAY_DB}` is hardcoded in ~5 places in `pg-provision.ts`, and nothing may assume a stable host or the upgrade path gets unpicked under pressure; (2) `max_replication_slots` defaults to **10** and zero-cache needs one slot per Deployment, so the 11th Deployment cannot start — set it at cluster provisioning (a restart) and track slot usage as a capacity metric from week one. **`CREATE EXTENSION vector` must move off the Deployment boot path**: it needs SUPERUSER, and on a shared cluster one superuser credential covers every Deployment's database — so a Deployment holding it could read every **Organization**'s data. Provisioning creates the extension (Control plane); the Deployment's `checkDeps` only _verifies_ it and fails with an actionable error; the Deployment's own role stays non-superuser and scoped to its database. Accepted risk: isolation between Organizations is credential-only at the network layer until a Deployment is upgraded to a dedicated server — which makes the builder→no-Postgres network denial the only barrier between a compromised build and every other Organization's data.
- **Builder hardening, all five agreed as launch work.** (1) **Scrubbed environment** — the builder container gets an explicitly-constructed env, never `{...process.env}` (which today carries `DATABASE_URL` and the daemon secret, readable by any postinstall script in a customer lockfile) and never the `$SHELL -ilc` captured login-shell env, which is both a liability and meaningless in a container. (2) **Egress deny-by-default** with an allowlist of the git host and package registries — verify the allowlist is destination-based and does not permit link-local, because the cloud metadata endpoint (`169.254.169.254`) is an account-level rather than Deployment-level compromise. (3) **Container per Builder task**, not per turn: the worktree must survive turns, and `.git/hooks/*` plus `node_modules` are executable surfaces that survive a reattached volume — so state the guarantee honestly as "bounded to one assignment," and add `.git/hooks` to the M1 deny-list. (4) **Per-Organization network isolation**: deny builder→any Postgres, cross-Organization reachability, and builder→Control plane/webhook shim. (5) **Repo allowlist in two layers** — the GitHub App installation is the outer boundary, an admin-configured list inside it is the inner one (today `workspace.ts` takes a `baseRepo` path or URL with no authorization notion at all), with **per-task tokens scoped to a single repo** and `contents: write` + `pull_requests: write` only, so Friday opens branches and PRs and never pushes to a default branch.
- **Builders are Friday-hosted at launch.** Customer-hosted runners and fully self-hosted Deployments are enterprise upgrades, not requirements — a customer-installed component is too much friction for initial use. Self-hosting needs a second mode for five things: auth (standalone BetterAuth + the customer's own SSO, rather than the Control plane as IdP), webhooks (the customer creates their own Slack/GitHub/Linear apps, since a distributed app has one event URL), capacity (`byo` — already exists), secret-key injection (pluggable, not one cloud's API), and licensing (no usage telemetry reaches us). Operationally it means version skew we do not control, boot-time migrations running unsupervised on customer data, and no observability. **Keep `friday setup` and convert it rather than deleting it in the local-first cleanup** — it is the enterprise install path. Design constraint to hold now, cheaply: keep the auth source and the webhook source as pluggable seams so the Deployment can boot, authenticate, and receive a webhook standalone. The dev container from the Q2 decision and the self-hosted artifact are the same image; let them diverge and this becomes a second product.
- **Secrets: keep the age vault, inject the key at runtime.** The defect containerization introduces is that `~/.friday/.age-key` would sit on the same persistent volume as the `vault.enc` it decrypts — obfuscation, not encryption at rest. Fix: the age identity comes from the platform secret manager into memory or tmpfs, never onto the volume, and the five auto-generated platform secrets (`BETTER_AUTH_SECRET`, `ZERO_AUTH_SECRET`, `ZERO_ADMIN_PASSWORD`, the daemon secret, VAPID) move to the secret manager rather than being written to `~/.friday/.env.local` on first boot. The split to hold: **platform secrets in the platform's manager, customer integration secrets in the customer's vault** — which keeps `secrets_fetch_log` and the rate-limited `friday-secrets` tool working unchanged, both of which matter more in SaaS than on a laptop. Rejected: serving secrets from the **Control plane**, because they are read on every integration-touching turn and the Control plane must stay out of the hot path (it provisions and bills; the Q16 webhook shim is the one forced exception).
- **`.daemon-secret`'s `0600` check is a crash-loop risk under container mounts.** `getDaemonSecret()` reads `~/.friday/.daemon-secret` and **fatally exits if any group or other permission bit is set**. Volume and secret mounts do not reliably preserve file modes, so this either keeps working or crash-loops every Deployment on boot depending on the mount implementation — and the failure mode is a hard exit with no degraded path. Verify against the real mount before first deploy; if the mode cannot be guaranteed, the check needs to move to "is this value present and well-formed" with the confidentiality guarantee coming from the mount rather than from `stat`.
- **Agent isolation becomes a prerequisite, not an optimization.** `sandbox-exec` is
  macOS-only and fails _open_ on Linux, and only builders are sandboxed at all —
  every other agent type runs unsandboxed, as the daemon's OS user, with
  `permissionMode: "bypassPermissions"` and the daemon's `process.env`. Agent
  execution moves to per-turn worker containers (builders first).

## Watch list (no immediate trigger)

Tracked here for visibility. Promote to a phase when usage demands it.

- **Per-capability permissions** (the deferred option (c) from the Role design): a capability set per **User** checked at the MCP tool gate, replacing the coarse `admin | member` **Role**. Promote when a customer needs finer authority than two roles — the likely first ask is "members may use `friday-secrets` for _these_ secrets" or "members may spawn builders against _these_ repos."
- **Per-thread Conversations** (the rejected option (c) from the Transport design): a durable main **Conversation** per **User** plus ephemeral per-external-thread Conversations summarized back into it. Promote if the **Transport** layer turns out to hold a single self-contained topic per thread more often than not — i.e. if one continuous per-User thread proves to interleave unrelated work badly enough to hurt relevance or token cost. Needs a promotion/summarization mechanism that (a) does not.
- **Streaming Bash stdout in chat** — vs. the current "summary + DB-fetch on expand" model. Acknowledged interesting; not now.
- **Friday Apps v2** (ADR-021 v2 column): HTTP route mounting under `/apps/<id>/*` for TRMNL-style external surfaces; dedicated dashboard route with per-app drill-down; destructive UI actions behind confirmation modals; port the existing kitchen bare agent + meal memory entries + scheduled weekly schedule onto the platform once the MVP has lived a release cycle.
- **Friday Apps v3**: capability declarations (`network[]`, `filesystem[]`, `exec[]`) backed by sandbox-exec / landlock enforcement, gated on family-visibility landing. Trust-by-discipline holds at single-user scale until that point.
- **Declarative app migrations** (`memory.retag` etc.). Defer until an app demands one; the MVP's atomic install/uninstall is enough for the foreseeable future.
